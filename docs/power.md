- **ハブをつないでいると、5V が来ている。** OTG の電源付きハブが VBUS に 5V を返しており、VDD5V（ch15）が約 4.93 V、`HW_POWER_STS` の VBUSVALID が立っている。電池の減りを測るときは、ハブも USB ケーブルも外す
- **BATT 端子（LRADC ch7）は電池の電圧ではない。** 単 3 アルカリで、電池だけで動かしても 3.38〜3.43 V でほぼ一定、負荷をかけても下がらない（下の測定）。電池を昇圧したあとの一定の電圧が来ていると考えられる。残量の目安にならない
- 5V があるときの電源の経路: `HW_POWER_DCDC4P2` = 0x00c00000（ENABLE_4P2 と ENABLE_DCDC）、`HW_POWER_5VCTRL` = 0x24008113。5V から DCDC に給電できる設定だが、電池からどれだけ取っているかは未確認。ハブをつないだまま一日作業したあと、電池はほぼ空になっていた
  - 読み解き（i.MX28 リファレンスマニュアル 11.12.2・11.12.9、AN4199）: DCDC4P2 の DROPOUT_CTRL = 0（DC-DC の入力は 4P2）、CMPTRIP = 0（4P2 が BATT の 85% 以上なら 4P2 を使う）。つまり **i.MX28 の DC-DC はもう 5V（4P2 経由）で動いている**。ただし 5VCTRL の CHARGE_4P2_ILIMIT = 0x08 で、5V から取れるのは **100 mA まで**。それを超える分は 4P2 が下がって電池から取る。U-Boot の SPL は 0x3f（780 mA）まで上げる
  - **電池を抜いても USB だけで動く**（2026-10-13、上限 480 mA、ハブをつないだまま 30 秒ほど抜いて戻した）。液晶・Wi-Fi・SSH とも止まらず、BATT 端子も 3.5 V のまま。見張りピンは 1111 → 0011 → 0001 → 0000 と数秒おきに下がり、戻すと 1111。基板の電源も 5V から取れる。生の記録は `~/brain-audio/logs/battpull-2026-10-13.log`
  - 起動のしかたで値が変わる（WinCE が起動してからハブの 5V を挿した 2026-10-13 昼の 2 回目は 0x24027113 = 480 mA）。2026-10-13 昼に、電池を入れたまま USB 給電で起動したときは `5VCTRL` = 0x24027111（上限 0x27 = 480 mA）、`DCDC4P2` = 0x10c01600（DROPOUT_CTRL = 1: 4P2 を使い、4P2 が BATT より低いときだけ電池も使う）。Linux はこれらを触らないので、WinCE が最後に書いた値のまま
  - STS の DCDC_4P2_BO・VDDD_BO などは常に 1 で、使えない。`MINPWR` = 0x00001040 の PWD_BO で、電圧低下を見る回路が止まっている
  - `userspace/power/pwrpath.py`: 電源レジスタを読んで、DC-DC の入力・5V の電流上限・STS のビットが立つ割合を出す（root、読むだけ）。`--load` で CPU に負荷をかけながら測る
  - 2026-10-13 夕方、ハブをつないだまま `systemctl reboot` したときは 0x20（400 mA）だった。起動前から 5V があるときの値は一定ではないらしい
  - **`brain-5v-ilimit`（起動時のサービス）で上限を 480 mA（0x27）に上げる。** 下げることはしない。上の再起動で `0x24020111 -> 0x24027111` と上げたのを確認。`/dev/mem` に 32 ビット 1 回で書く（C。Python の mmap への書き込みは 1 回の 32 ビットになる保証がない）
  - **動いている最中に上限を下げない。** 試験のために 480 → 100 mA に下げたら、弱った電池では足りず 5 秒以内に止まった（2026-10-13。新しい電池に替えるまで起動しなかった）
  - 2 回目（2026-10-13）: ハブをつないだまま（`src=5v`）でも、見張りピンが 1111 → 0011 → 0001 → 0000 と下がり、0000 になって 17 分後に止まった（メイン液晶は真っ白、入/切も効かない。カーネルのメッセージは何も残っていない）。リセットで起こすと WinCE は 1 段・× なし、Linux は 0111。アルカリ電池は休ませると少し戻る。**上限 100 mA のままでは、ハブの 5V があっても電池は減る**（このときの上限は記録していないが、ゆうべの起動も 100 mA だったと見ている）。480 mA にしてからは、ハブの 5V で 70 分（2026-10-13 18:22〜19:33）使って見張りピンは 1111 のままだった。直前の眠りから起きたときは同じ電池で 0111 と 1111 の境目だったので、少なくとも減りは小さい
  - 3 回目（2026-10-15、上限 480 mA）: ハブをつないだまま、pmd-app で曲を鳴らしたり SSH で読んだりしている間に、0011 → 0001（21:28）→ 0000（21:42 から揺れ、21:51 から 0000 のまま）と下がり、22:02 過ぎに止まった（journal の最後は 22:02:32。電池に ×、画面がちらついて真っ白、のちに暗くなる。サブ液晶のバックライトは点いたまま）。**480 mA でも、使っていればハブの 5V があっても電池は減る**。取り出した電池はかなり熱くなっていた（本人）。替えたあとの起動でレジスタを読むと、CHARGE = 0x10000（PWD_BATTCHRG = 1、BATTCHRG_I = 0。i.MX28 の充電器は止まっていて、電池に流し込んではいない）、THERMAL = 0x80（温度センサーは電源が切れている。STS の THERMAL_WARNING も 0）。i.MX28 の温度で落ちる仕組みは働いていないので、止まったのは電池が尽きたためと見ている。電池が熱くなるのは、空に近いアルカリ電池から電流を取り続けたため（電圧が下がると同じ電力に要る電流が増え、内部抵抗も大きくなる）と考えている。メイン液晶やバックライトなど、i.MX28 の電源の外にあって電池から直接取る部分があるのかもしれない（確かめていない）。**見張りピンが 0000 になったら、早めに電池を替える**（空のアルカリ電池を入れたままにしない）

- **電池の残量は GPIO4_4・GPIO4_6・GPIO4_7・GPIO4_8 でわかる。** どれも GPIO の入力で、電池が減ると 0 になる。ほぼ空のアルカリ電池で 4 本とも 0、新しいアルカリ電池に替えると 4 本とも 1 になった（2026-10-12、5V はつないだまま）。電圧の数値は取れず、段階だけ。どのピンがどの順で落ちるかは、電池を使い切りながら記録して確かめる
  - `userspace/power/battpins.c`: `HW_PINCTRL_DIN4` を `/dev/mem` から読むだけ（root、何も変えない）。`arm-linux-gnueabi-gcc -O2 -march=armv5te -static` でビルドして `/usr/local/bin/battpins` に置く。libgpiod のコマンドは Brainux に入っていない

`userspace/power/brain-power.sh` が 1 行で出す（root でなければ pins は出ない）。`brain-watch.sh` も 10 秒ごとに同じものを記録する（`pwr=[...]`）。

```
src=5v batt=3412mV 5v=5002mV vddd=1559mV vddio=3216mV pins=1111
```

pins は GPIO4_4・4_6・4_7・4_8 の順。

## サスペンド（2026-10-12、動いた）

蓋を閉じると眠り、開けると 1 秒以内に起きる。キーを押しても起きる。カーネルのパッチ 2 つと設定 1 つ（[install.md](install.md) の手順 2）。

| 何が足りなかったか | 直し方 |
|---|---|
| 蓋の開閉は、キーボードのマイコン（I2C0 の 0x28）からスイッチのコード 3 で届いていた（閉じると on、開けると off）。`brain-kbd-i2c` はこれを「液晶をタブレットの形に回した」として捨てていた。GPIO には変化なし | `kernel/0003`: DT の `lid-switch-code = <3>` で、そのコードを `SW_LID` として出す。systemd-logind が蓋を閉じたら眠らせる（既定の `HandleLidSwitch=suspend`） |
| キーボードのマイコンの割り込みが起床に使われていなかった | `kernel/0003`: DT に `wakeup-source`。キーと蓋を開けたときの割り込みで起きる |
| `deep` で眠ると 1 秒で起きた、と見えた（2026-10-15 に訂正: 起きていたのではなく、眠っていた時間が時計に足されていなかった。下の「deep を試し直した」） | s2idle にした（`brain-s2idle.conf`）。2026-10-15 に 0009 で `deep` を作ってからは `deep`（`system/etc/systemd/sleep.conf.d/brain-sleep-mode.conf`、下の「deep を作る」） |
| 眠ってもメイン液晶のバックライトが消えなかった。明るさ 0 でも変わらない（1 だとほぼ消える） | `kernel/0002`: i.MX28 の PWM は、止めると最後の出力レベルを保ったままになる。明るさ 7（デューティ 100%）から止めると点きっぱなし。止める前に出力を消灯側に固定し、2 周期待ってから止める |
| 起きたあと音が出なかった（2026-10-14 に見つけた。下の「起きたあと I2C の DMA が止まる」） | `kernel/0008`: mxs-dma の resume で DMA のブロックをリセットしない |

確かめたこと（PW-A9300、電源付きハブ・Wi-Fi 子機をつないだまま）:

- `systemctl suspend` → 約 25 秒眠り、キーで起きた。眠っている間、メインのバックライトは消えていた
- 蓋を閉じる → 約 8 秒後に眠った（NetworkManager などの準備に数秒かかる）→ 約 14 秒後に蓋を開けた瞬間に起きた。journal は `Lid closed.` → `PM: suspend entry (s2idle)` → `Lid opened.` → `PM: suspend exit`
- 起きたあと、Wi-Fi 子機（ハブの先）は USB のリセットを経て数秒でつながり直した
- 明るさ 0 で、メインのバックライトが消えた

わかったこと・罠:

- **この機種の s2idle は時計を止めない。** `CONFIG_CPU_IDLE` が無効なので（`kernel/sched/idle.c` の `cpuidle_not_available` の道を通る）、s2idle は「プロセスを止め、デバイスを眠らせ、WFI で待つ」だけで、CLOCK_MONOTONIC も CLOCK_BOOTTIME も進み続ける。眠っていた時間は時計の差では測れない。`userspace/power/sleepwatch.py` は 1 秒ごとのループの間が空いたことで測る。タイマーの割り込みでも CPU はときどき WFI から出る（すぐまた眠る）ので、眠っている間の電力はもっと下げられる余地がある
- `systemctl suspend` は眠るのを待たずに戻る。スクリプトで「起きたら」を書くときは注意
- journal の時刻: 眠る直前のカーネルのメッセージ（`Freezing ...` など）は、起きたあとに journald が読むので、起きた時刻が付く
- メインのバックライトの DT（`imx28-brain.dtsi`）にある `enable_gpios` は綴りが違い（`pwm-backlight` が読むのは `enable-gpios`）、使われていない。GPIO3_5 を 1 にするとバックライトがさらに明るくなった。点灯のピンではなく、バックライトの電流のモードを切り替えるピン（linux-brain PR #36 で「current-mode」として割り当てられたもの。綴りの違いで今は使われていない）。消費電力が増えるので、理由がなければ触らない
- 蓋の試験のあと開けたまま置いていたら、バックライトが消え、キーで 1 秒以内に戻った。サスペンドではない（journal に眠った記録がなく、`sleepwatch.py` も止まらずに動き続けていた）。X のスクリーンセーバー（600 秒で画面を消す）と DPMS（600 秒）が有効なので、最後のキー操作から 10 分で X が消したもの。蓋を開けたことは X の操作に数えられない。Brainux には `xset` がないので、libX11 の `XGetScreenSaver` と libXext の `DPMSGetTimeouts` を python の ctypes から呼んで確かめた
- 「入/切」ボタン（`KEY_POWER`）: Brainux の既定では押すと電源が切れる。`system/etc/systemd/logind.conf.d/brain-power-key.conf` で、短く押すと眠る（`HandlePowerKey=suspend`）、長押し（約 5 秒）で電源オフ（`HandlePowerKeyLongPress=poweroff`）にした。`sudo systemctl kill -s HUP systemd-logind` で再起動なしに効く
  - 試した結果: 短く押す → 約 5 秒後に眠った（NetworkManager の待ち合わせが 5 秒で打ち切られるまで待つ）→ もう一度押す → 起きた
  - 長押し: 5 秒で `Power key pressed long.` となり電源オフが始まる。電源が実際に切れるまでさらに 10 秒ほどかかるので、押している側には 5 秒より長く感じる
- **起こしたときの「入/切」を捨てる（`kernel/0003` に含む）。** 起こした押下がそのまま logind に届くと、新しい「眠れ」（押し続ければ「電源オフ」）と取られうる。logind は長押しを設定していると、短押しかどうかを離した時点で決める。0003 の前の試験では、起こした押下は離した時点でまだサスペンドの後始末中（`Operation 'suspend' finished.` の 3 秒前）だったので無視されていたが、3 秒以上押してから離せば眠り直す計算だった
  - 0003 では、サスペンドに入るときに構え、起きて最初の「入/切」の押下を離すまで捨てる。ほかのキーが押されるか、起きてから 1 秒たてば構えを解く（蓋で起きたときに、次の「入/切」を捨てないため）
  - 確かめたこと: 眠らせ、「入/切」を 3〜4 秒押し続けてから離して起こす → 眠り直さない。journal にも起こした押下は出ない。そのあと短く押す → ふつうに眠る
- 眠っている間にどれだけ電池が減るかは未測定

### deep を試し直した（2026-10-15）

`echo deep > /sys/power/mem_sleep; echo mem > /sys/power/state` を 2 回（ハブ・Wi-Fi 子機つき）。

- journal では `PM: suspend entry (deep)` から約 2 秒で `PM: suspend exit` なので「すぐ起きた」ように見えるが、どちらもキーを押すまで眠っていた（本人が画面を見て確かめた。10 分で X が画面を消すのとは別）。そのあと Brain の時計が Chromebook より約 3 分、約 9 分遅れていた（眠っていた時間の分）
- 理由: Brain の DT では RTC（`rtc@80056000`）が `disabled` で、`/sys/class/rtc` が空。`deep` ではタイマーも止まるので、眠っていた時間を知る手段がなく、時計がその分止まる（s2idle では時計は進み続ける）。NTP がつながれば直るが、ふだん使いでは困る
- 2026-10-12 の「`deep` は 1 秒で起きる」も同じ見かけだった可能性が高い。起こす合図（キーボードのマイコンの割り込み）は `deep` でも効いている
- `deep` を使うなら、眠っていた時間を時計に足す仕組みが要る。RTC のドライバ（rtc-stmp3xxx）は probe でブロックをリセットするので、WinCE やブートローダーが使っているかもしれない持続レジスタへの影響を確かめてから。RTC の秒のカウンタ（`HW_RTC_SECONDS`）を読むだけの persistent clock を足すほうが軽い
- Wi-Fi: 1 回目は起きたときの probe が -11 で失敗し、`brain-wifi-reprobe` がポートの電源を切ったが、子機が見つかり直さなかった（2 分以上。抜き差しで戻った）。ハブ（`1-1`）は runtime PM が `auto`・待ち時間 0 で、子機がいなくなると眠り、起きた直後はつながったことを拾えなかったと見ている。電源を切り直す間はハブと上流を `power/control = on` にし、子機が戻るまで最大 10 秒待つようにした。2 回目（起きたあとドライバを外して同じ失敗を作った）は、電源が戻って 1 秒で子機が見つかり直し、約 13 秒でつながった

### deep を作る（kernel/0009、2026-10-15、実機で level 0〜2 を確かめた）

`deep` を s2idle より深くする。手本は Freescale の 2.6.35 BSP の `mx28_cpu_standby`（`arch/arm/mach-mx28/sleep.S`、GPL）と、それを 3.10 の `mach-mxs` に移した Digi の版（`digidotcom/yocto-linux` の `arch/arm/mach-mxs/mx28-sleep.S`）。手元の写しは `~/brain-audio/ref/mx28-pm/`。

- `arch/arm/mach-mxs/suspend-mx28.S`（196 バイト）を起動時に OCRAM（物理 0x8000、`__arm_ioremap_exec` + `fncpy`）へ写し、`suspend_ops->enter` から呼ぶ。中でやること: CPU を 24 MHz の水晶へ（`CLKSEQ` の BYPASS_CPU）→ DRAM をセルフリフレッシュに（`HW_DRAM_CTL22` の LOWPOWER_CONTROL = 2、少し待つ）→ EMI のクロックと、CPU・EMI の分数分周器を止める →（level 2）PLL0 を止め、HBUS を 1/31 に → WFI → 逆の順に戻す
- MMU は入れたまま、レジスタは ioremap のアドレスで触る。最初に各レジスタのページを読んで TLB に載せ、セルフリフレッシュの間は DRAM に一切触れない（スタックもリテラルプールも使わない。逆アセンブルで再配置なしを確かめた）
- Freescale・Digi と違い、VDDD・VDDA・VDDIO は下げず、DC-DC の設定（MINPWR・LOOPCTRL）も触らない（NXP のフォーラムに「5V だけのときに電圧を下げると固まる」報告。まず動かすことを優先）。5V の電流上限（ILIMIT_EQ_ZERO）も触らない
- 眠っていた時間: RTC の秒のカウンタ（`HW_RTC_SECONDS`、読むだけ）を眠る前と起きたあとで読み、`.wake` で `timekeeping_inject_sleeptime64()` に渡す。RTC のドライバは使わない

- メイン液晶（PW-A9300 の `brain-lq050j1ug01`）は画面を自分で覚えていて、LCDIF は書き換えのときだけ DRAM を読む。眠っている間はプロセスもコンソールも止まっているので、手当てしていない

### 起きたあと I2C の DMA が止まる（2026-10-14、kernel/0008 で直した）

症状: 眠って起きたあと、最初に音を出そうとすると aplay が `Unable to install hw params` で失敗する。dmesg は `ymu818 0-003a: section 1 failed at op 10: -110`。再起動するまで戻らない。同じ I2C0 のキーボード・タッチは動いている。

調べたこと:

- 眠る前と起きたあとで、クロック（PLL0・SAIF0 の MCLK・DIGCTL）、SAIF0・I2C0・APBX DMA のレジスタ、ピンの割り当て、YMU818 のリセットの線は同じだった。YMU818 は起きたあとも読みに答えた（reg 0 = 3b）。チップとクロックの問題ではない
- i2c-mxs は、読みは 5 バイト以上、書き込みは 7 バイト以上で DMA を使う（それより短いと PIO）。起きたあと、YMU818 から 1・4 バイトの読みは通り、8・16 バイトの読みは毎回 1 秒待って -110 になった。キーボード・タッチは短い読みだけなので動いていた。YMU818 の初期化は、2 本目の長い書き込み（op 10）で止まる
- i2c-mxs は DMA の最中に止まると、何が起きても（NAK でも）1 秒待って -ETIMEDOUT を返す。-110 は「I2C の線がタイムアウトした」とは限らない
- 止まったあとの APBX の ch6（I2C0）は、周辺装置からの要求を待つ状態のまま、`SEMA` に起こされた転送がたまっていた。命令レジスタには i2c-mxs が書くはずのない長さが載っていた。ch6 だけリセットしても、次の転送でまた止まった

原因: linux-brain の mxs-dma には、上流（v6.1 も最新も）にない runtime PM とスリープの処理がある（NXP のベンダーカーネル由来と見られる）。その resume は `mxs_dma_init()` を呼び直し、APBH・APBX のブロック全体を `stmp_reset_block()` でリセットする。i2c-mxs（probe で）と SAIF の PCM（登録時に）はチャンネルを握ったままなので、その下でブロックの中身を消すと、DMA の機械とドライバの持っている状態が食い違う。s2idle ではブロックの電源も中身も残るので、リセットは要らない。

直し方（`kernel/0008`）: スリープの処理を `pm_runtime_force_suspend` / `pm_runtime_force_resume` にした（眠る間にクロックを止めることは残し、起きたときのリセットはやめた）。眠る前・起きたあとの 8・16 バイトの読みが通り、起きたあとの YMU818 の初期化と 3 秒の再生（イヤホン・無音）が通った。蓋で眠らせて起こしたあと、イヤホンで曲（pmd-hle の CANON.M）が鳴るのを本人が耳で確かめた。

## CPU クロックを変える手がかり

- クロックの木は分周で下げられる: `cpu_pll` の分周（`HW_CLKCTRL_CPU` の DIV_CPU、6 ビット）を変えれば 454.7 / 227.4 / 151.6 / … MHz。`mxs_clk_div` は `set_rate` を持つ
- HBUS は CPU から分周しているので、CPU を下げると HBUS（DMA・LCD・SD などのバス）も下がる。LCD のちらつき・音の途切れに注意
- 2015 年に上流へ i.MX23/28 の cpufreq-dt 対応（VDDD などの mxs レギュレーター + OPP）が提案されている。OPP は 261.8 / 360 / 392.7 / 454.7 MHz を 1.35 / 1.35 / 1.45 / 1.55 V。レビューで「EMI が 196 MHz を超えるなら VDDD を 1.55 V より下げない」という指摘あり。NXP のフォーラムには 454.7 MHz 以外で固まったという報告もある
- 電圧を下げないと、クロックを下げても省電力の効きは小さい（アイドル時は WFI で止まっているので、もともと CPU はあまり食っていない）

## 進め方（案）

1. 測り方: 電池の見張りピンが落ちるまでの時間で比べる（粗いが実際の持ち時間がわかる。USB 電流計はない）
2. 何が電気を食っているかを先に見る（バックライト、Wi-Fi、CPU の負荷）
3. CPU クロック: 電圧はそのままで分周だけ下げ、安定するか見る → VDDD も下げる
4. サスペンド: 蓋と入/切で眠って起きるところまでできた（上）。`deep` を深くするパッチ（0009）で、DRAM をセルフリフレッシュにして眠り、キーで起きるところまで確かめ、眠り方の既定を `deep` にした（上の「deep を作る」）。眠っている間の電池の減りは、テスターがないので見張りピンで粗く比べる
5. 電池残量: 見張りピンの 4 段階を Linux の power_supply として見せる（小さなドライバか、ユーザー空間で）
