# CPU クロックと電源

WinCE の解析とつながる部分（5V から取る電流と 4P2、電池の見張りピンと電圧、`deep` を作る `kernel/0009`）は [power-wince.md](power-wince.md) に分けた。Brainux にそれらのコードを書こうとしている方は、そちらを読まないでください（[README](../README.md) の注意）。この文書の残りは、WinCE の解析を使っていない。

## 今の状態（2026-10-12、Brainux 標準の設定 + このリポジトリのカーネル）

| 項目 | 値 | 読み方 |
|---|---|---|
| CPU | 454.7 MHz 固定（ref_cpu = PLL 480 MHz × 18/19、cpu_pll 分周 1） | `/sys/kernel/debug/clk/clk_summary` |
| HBUS | 151.6 MHz（CPU の 1/3） | 同上 |
| EMI（DRAM） | 196.4 MHz | 同上 |
| VDDD（コア電圧） | 1.55 V（`HW_POWER_VDDDCTRL` = 0x0002071e、TRG = 30） | LRADC ch13 でも 1.557 V |
| VDDIO / VDDA | 3.2 V / 1.79 V | ch10 / ch12 |
| cpufreq | なし（`CONFIG_CPU_FREQ` が無効、imx28.dtsi に OPP もない） | |
| サスペンド | s2idle で動く（下の「サスペンド」）。`deep` は元の mxs では `cpu_do_idle()`（WFI 1 回）を呼ぶだけで、RTC が DT で無効なので眠っていた時間が時計から抜けた（下の「deep を試し直した」）。kernel/0009 で DRAM のセルフリフレッシュと PLL0 止めまで入れ、眠っていた時間も足すようにした（実機で level 0〜2 を確認。[power-wince.md](power-wince.md) の「deep を作る」） | |
| 電源断 | `poweroff` は syscon-poweroff（`HW_POWER_RESET` に PWD）。電池だけのとき、これで電源が切れ、「入/切」で起動できる（2026-10-12 に確認。起動は WinCE のメニューから Brainux を選ぶいつもの流れ） | |
| 電池残量 | `/sys/class/power_supply` がない。電池の見張りピンで段階的にわかる（[power-wince.md](power-wince.md)） | |

- **ハブをつないでいると、5V が来ている。** OTG の電源付きハブが VBUS に 5V を返しており、VDD5V（ch15）が約 4.93 V、`HW_POWER_STS` の VBUSVALID が立っている。電池の減りを測るときは、ハブも USB ケーブルも外す
- **BATT 端子（LRADC ch7）は電池の電圧ではない。** 単 3 アルカリで、電池だけで動かしても 3.38〜3.43 V でほぼ一定、負荷をかけても下がらない（下の測定）。電池を昇圧したあとの一定の電圧が来ていると考えられる。残量の目安にならない

## 電池だけでの負荷試験（2026-10-12、方法が使えないとわかった）

`userspace/power/loadtest.sh` で、ハブを外して状態を 45 秒ずつ切り替え、BATT 端子の電圧を 1 秒ごとに記録した（後半 30 秒の中央値）。

|---|---|
| 基準（バックライト 7/7、サブ 3/3） | 3390 mV |
| メインのバックライトを消す | 3391 mV |
| 基準 | 3392 mV |
| サブのバックライトを消す | 3395 mV |
| 基準 | 3391 mV |

| 基準 | 3388 mV |
| MUCOM88 の再生（スピーカー） | 3413 mV |

## サスペンド（2026-10-12、動いた）

蓋を閉じると眠り、開けると 1 秒以内に起きる。キーを押しても起きる。カーネルのパッチ 2 つと設定 1 つ（[install.md](install.md) の手順 2）。

| 何が足りなかったか | 直し方 |
|---|---|
| 蓋の開閉は、キーボードのマイコン（I2C0 の 0x28）からスイッチのコード 3 で届いていた（閉じると on、開けると off）。`brain-kbd-i2c` はこれを「液晶をタブレットの形に回した」として捨てていた。GPIO には変化なし | `kernel/0003`: DT の `lid-switch-code = <3>` で、そのコードを `SW_LID` として出す。systemd-logind が蓋を閉じたら眠らせる（既定の `HandleLidSwitch=suspend`） |
| キーボードのマイコンの割り込みが起床に使われていなかった | `kernel/0003`: DT に `wakeup-source`。キーと蓋を開けたときの割り込みで起きる |
| `deep` で眠ると 1 秒で起きた、と見えた（2026-10-15 に訂正: 起きていたのではなく、眠っていた時間が時計に足されていなかった。下の「deep を試し直した」） | s2idle にした（`brain-s2idle.conf`）。2026-10-15 に 0009 で `deep` を作ってからは `deep`（`system/etc/systemd/sleep.conf.d/brain-sleep-mode.conf`、[power-wince.md](power-wince.md) の「deep を作る」） |
| 眠ってもメイン液晶のバックライトが消えなかった。明るさ 0 でも変わらない（1 だとほぼ消える） | `kernel/0002`: i.MX28 の PWM は、止めると最後の出力レベルを保ったままになる。明るさ 7（デューティ 100%）から止めると点きっぱなし。止める前に出力を消灯側に固定し、2 周期待ってから止める |
| 起きたあと音が出なかった（2026-10-14 に見つけた。下の「起きたあと I2C の DMA が止まる」） | `kernel/0008`: mxs-dma の resume で DMA のブロックをリセットしない |

確かめたこと（PW-A9300、電源付きハブ・Wi-Fi 子機をつないだまま）:

- `systemctl suspend` → 約 25 秒眠り、キーで起きた。眠っている間、メインのバックライトは消えていた
- 蓋を閉じる → 約 8 秒後に眠った（NetworkManager などの準備に数秒かかる）→ 約 14 秒後に蓋を開けた瞬間に起きた。journal は `Lid closed.` → `PM: suspend entry (s2idle)` → `Lid opened.` → `PM: suspend exit`
- 起きたあと、Wi-Fi 子機（ハブの先）は USB のリセットを経て数秒でつながり直した
- 明るさ 0 で、メインのバックライトが消えた

わかったこと・罠:

- **この機種の s2idle は時計を止めない。** `CONFIG_CPU_IDLE` が無効なので（`kernel/sched/idle.c` の `cpuidle_not_available` の道を通る）、s2idle は「プロセスを止め、デバイスを眠らせ、WFI で待つ」だけで、CLOCK_MONOTONIC も CLOCK_BOOTTIME も進み続ける。眠っていた時間は時計の差では測れない。`userspace/power/sleepwatch.py` は 1 秒ごとのループの間が空いたことで測る。タイマーの割り込みでも CPU はときどき WFI から出る（すぐまた眠る）ので、眠っている間の電力はもっと下げられる余地がある
- `systemctl suspend` は眠るのを待たずに戻る。スクリプトで「起きたら」を書くときは注意
- journal の時刻: 眠る直前のカーネルのメッセージ（`Freezing ...` など）は、起きたあとに journald が読むので、起きた時刻が付く
- メインのバックライトの DT（`imx28-brain.dtsi`）にある `enable_gpios` は綴りが違い（`pwm-backlight` が読むのは `enable-gpios`）、使われていない。GPIO3_5 を 1 にするとバックライトがさらに明るくなった。点灯のピンではなく、バックライトの電流のモードを切り替えるピン（linux-brain PR #36 で「current-mode」として割り当てられたもの。綴りの違いで今は使われていない）。消費電力が増えるので、理由がなければ触らない
- 蓋の試験のあと開けたまま置いていたら、バックライトが消え、キーで 1 秒以内に戻った。サスペンドではない（journal に眠った記録がなく、`sleepwatch.py` も止まらずに動き続けていた）。X のスクリーンセーバー（600 秒で画面を消す）と DPMS（600 秒）が有効なので、最後のキー操作から 10 分で X が消したもの。蓋を開けたことは X の操作に数えられない。Brainux には `xset` がないので、libX11 の `XGetScreenSaver` と libXext の `DPMSGetTimeouts` を python の ctypes から呼んで確かめた
- 「入/切」ボタン（`KEY_POWER`）: Brainux の既定では押すと電源が切れる。`system/etc/systemd/logind.conf.d/brain-power-key.conf` で、短く押すと眠る（`HandlePowerKey=suspend`）、長押し（約 5 秒）で電源オフ（`HandlePowerKeyLongPress=poweroff`）にした。`sudo systemctl kill -s HUP systemd-logind` で再起動なしに効く。2026-10-16 から、短押しは subpaneld が円と月を出してから眠りを頼む（`HandlePowerKey=ignore`。docs/subpanel.md「入/切と眠り」）
- 眠るまでを縮めた（2026-10-16）: 入/切を押してから眠りに入るまで約 10 秒かかっていた。内訳は、NetworkManager が Wi-Fi を切るまで眠りを待たせる delay の inhibitor が既定の上限 5 秒いっぱい（その中で NetworkManager-dispatcher の起動に 3 秒。Brain には dispatcher のスクリプトが 1 つもない）、そのあとディスクへの書き出し（1.5 秒）などで約 4 秒。`system/etc/systemd/logind.conf.d/brain-sleep-delay.conf`（`InhibitDelayMaxSec=1`）と `systemctl mask NetworkManager-dispatcher.service` で、離してから眠りに入るまで 2〜5 秒になった。Wi-Fi の子機は起きるたびに読み込み直すので、切り終わるのを待つ意味は小さい
- logind は起きてから `HoldoffTimeoutSec`（既定 30 秒。外付けのモニターを見つけるための待ち）の間、蓋を無視し、過ぎてから閉じていれば眠る。起きた直後に閉じた蓋が 30 秒後まで効かなかったので、`brain-lid.conf` で 5 秒にした。2026-10-16 朝の「起きて 25 秒後にまた眠った」も、この待ちのあとだった
  - 試した結果: 短く押す → 約 5 秒後に眠った（NetworkManager の待ち合わせが 5 秒で打ち切られるまで待つ）→ もう一度押す → 起きた
  - 長押し: 5 秒で `Power key pressed long.` となり電源オフが始まる。電源が実際に切れるまでさらに 10 秒ほどかかるので、押している側には 5 秒より長く感じる
- **起こしたときの「入/切」を捨てる（`kernel/0003` に含む）。** 起こした押下がそのまま logind に届くと、新しい「眠れ」（押し続ければ「電源オフ」）と取られうる。logind は長押しを設定していると、短押しかどうかを離した時点で決める。0003 の前の試験では、起こした押下は離した時点でまだサスペンドの後始末中（`Operation 'suspend' finished.` の 3 秒前）だったので無視されていたが、3 秒以上押してから離せば眠り直す計算だった
  - 0003 では、サスペンドに入るときに構え、起きて最初の「入/切」の押下を離すまで捨てる。ほかのキーが押されるか、起きてから 1 秒たてば構えを解く（蓋で起きたときに、次の「入/切」を捨てないため）
  - 確かめたこと: 眠らせ、「入/切」を 3〜4 秒押し続けてから離して起こす → 眠り直さない。journal にも起こした押下は出ない。そのあと短く押す → ふつうに眠る
- **眠りに入る途中で蓋を開けると、開いたまま眠る**（2026-10-16、蓋を閉じたまま鳴らす再生アプリの試験で見つけた）。蓋を閉じたまま、鳴らしているイヤホンを抜いたら、アプリが蓋の inhibitor を外して logind が眠り始めた（17:19:18 `Suspending...`）。約 6 秒後（`PM: suspend entry (deep)` の直後、ディスクへの書き出しの間）に蓋を開けたが、そのまま眠り、サブ液晶は月、メイン液晶は消えたままだった。蓋を開けた知らせは logind にも subpaneld にも届いている（`Lid opened.`）。logind は眠り始めたら蓋を開けても取りやめず、`brain-kbd-i2c` も割り込みで `pm_wakeup_event` を出さないので、カーネルも取りやめない。蓋が開いた割り込みは眠る前に済んでいるので、起こす割り込みも来ない。このときはイヤホンを挿したら起きた（[audio-ymu818.md](audio-ymu818.md)）。キーか「入/切」を押しても起きるはず。蓋を閉じてすぐ開けたときも同じことが起こりうる（logind が眠り始めてからデバイスが眠るまで、Brain では約 6 秒ある）。直すなら 0003 で、眠り始めてから蓋が開いたら、キーボードを眠らせるところ（`bk_i2c_suspend`）で断って（`-EBUSY`）取りやめる。`pm_wakeup_hard_event` だけでは、書き出しの間に来た分は `freeze_processes` の `pm_wakeup_clear` で消える。「眠り始め」をカーネルのどこで知るか（PM の通知は書き出しのあと）は考えが要る。本人と決めて、このままにする（2026-10-16）
- 眠っている間にどれだけ電池が減るかは未測定

### deep を試し直した（2026-10-15）

`echo deep > /sys/power/mem_sleep; echo mem > /sys/power/state` を 2 回（ハブ・Wi-Fi 子機つき）。

- journal では `PM: suspend entry (deep)` から約 2 秒で `PM: suspend exit` なので「すぐ起きた」ように見えるが、どちらもキーを押すまで眠っていた（本人が画面を見て確かめた。10 分で X が画面を消すのとは別）。そのあと Brain の時計が Chromebook より約 3 分、約 9 分遅れていた（眠っていた時間の分）
- 理由: Brain の DT では RTC（`rtc@80056000`）が `disabled` で、`/sys/class/rtc` が空。`deep` ではタイマーも止まるので、眠っていた時間を知る手段がなく、時計がその分止まる（s2idle では時計は進み続ける）。NTP がつながれば直るが、ふだん使いでは困る
- 2026-10-12 の「`deep` は 1 秒で起きる」も同じ見かけだった可能性が高い。起こす合図（キーボードのマイコンの割り込み）は `deep` でも効いている
- `deep` を使うなら、眠っていた時間を時計に足す仕組みが要る。RTC のドライバ（rtc-stmp3xxx）は probe でブロックをリセットするので、WinCE やブートローダーが使っているかもしれない持続レジスタへの影響を確かめてから。RTC の秒のカウンタ（`HW_RTC_SECONDS`）を読むだけの persistent clock を足すほうが軽い
- Wi-Fi: 1 回目は起きたときの probe が -11 で失敗し、`brain-wifi-reprobe` がポートの電源を切ったが、子機が見つかり直さなかった（2 分以上。抜き差しで戻った）。ハブ（`1-1`）は runtime PM が `auto`・待ち時間 0 で、子機がいなくなると眠り、起きた直後はつながったことを拾えなかったと見ている。電源を切り直す間はハブと上流を `power/control = on` にし、子機が戻るまで最大 10 秒待つようにした。2 回目（起きたあとドライバを外して同じ失敗を作った）は、電源が戻って 1 秒で子機が見つかり直し、約 13 秒でつながった

### 起きたあと I2C の DMA が止まる（2026-10-14、kernel/0008 で直した）

症状: 眠って起きたあと、最初に音を出そうとすると aplay が `Unable to install hw params` で失敗する。dmesg は `ymu818 0-003a: section 1 failed at op 10: -110`。再起動するまで戻らない。同じ I2C0 のキーボード・タッチは動いている。

調べたこと:

- 眠る前と起きたあとで、クロック（PLL0・SAIF0 の MCLK・DIGCTL）、SAIF0・I2C0・APBX DMA のレジスタ、ピンの割り当て、YMU818 のリセットの線は同じだった。YMU818 は起きたあとも読みに答えた（reg 0 = 3b）。チップとクロックの問題ではない
- i2c-mxs は、読みは 5 バイト以上、書き込みは 7 バイト以上で DMA を使う（それより短いと PIO）。起きたあと、YMU818 から 1・4 バイトの読みは通り、8・16 バイトの読みは毎回 1 秒待って -110 になった。キーボード・タッチは短い読みだけなので動いていた。YMU818 の初期化は、2 本目の長い書き込み（op 10）で止まる
- i2c-mxs は DMA の最中に止まると、何が起きても（NAK でも）1 秒待って -ETIMEDOUT を返す。-110 は「I2C の線がタイムアウトした」とは限らない
- 止まったあとの APBX の ch6（I2C0）は、周辺装置からの要求を待つ状態のまま、`SEMA` に起こされた転送がたまっていた。命令レジスタには i2c-mxs が書くはずのない長さが載っていた。ch6 だけリセットしても、次の転送でまた止まった

原因: linux-brain の mxs-dma には、上流（v6.1 も最新も）にない runtime PM とスリープの処理がある（NXP のベンダーカーネル由来と見られる）。その resume は `mxs_dma_init()` を呼び直し、APBH・APBX のブロック全体を `stmp_reset_block()` でリセットする。i2c-mxs（probe で）と SAIF の PCM（登録時に）はチャンネルを握ったままなので、その下でブロックの中身を消すと、DMA の機械とドライバの持っている状態が食い違う。s2idle ではブロックの電源も中身も残るので、リセットは要らない。

直し方（`kernel/0008`）: スリープの処理を `pm_runtime_force_suspend` / `pm_runtime_force_resume` にした（眠る間にクロックを止めることは残し、起きたときのリセットはやめた）。眠る前・起きたあとの 8・16 バイトの読みが通り、起きたあとの YMU818 の初期化と 3 秒の再生（イヤホン・無音）が通った。蓋で眠らせて起こしたあと、イヤホンで曲が鳴るのを本人が耳で確かめた。

### 眠っている間のハブの 5V と、起きたあとの Wi-Fi（2026-10-14〜15）

できごと: 蓋を閉じてすぐハブを抜き（部屋を移るため）、約 13 分眠らせ、蓋を開ける直前にハブを挿し直した。起きて画面が数秒見えたあと暗くなり、キー・タッチ・ネットワークとも反応がなくなった（サブ液晶はしばらく表示が残り、やがてバックライトも消えた。入/切でメインのバックライトは点いたが真っ白）。電池を抜いて起こした。

記録（`journalctl -b -1`、brain-watch.log）:

- 22:55:29 蓋を閉じる → 22:55:32 ハブが消える（本人が抜いた）→ 22:55:36 眠る → 23:08:24 蓋で起きる（ここまで正常）
- 起きた直後（23:08:25）は 5V なし・見張りピン `0000`。眠っている間は USB が止まっているので、挿し直したハブが見つかったのは起きて 8 秒後（23:08:32）、5V があったのは 23:08:37 の記録から
- 23:08:33 に Wi-Fi 子機のファームウェアを読み込んだところで journal が終わり、23:08:37〜48 の間に止まった。カーネルのメッセージは何も残っていない。止まり方は 2026-10-13 の「弱った電池で 5V を失った」ときと同じ
- 5V が戻ったあとで止まった理由は分からない（弱った電池から 5V へ切り替わるときの揺れか、子機の初期化の電流か）。弱った電池が要る場面なので追っていない

切り分け（`userspace/power/vbuswatch.py` で 0.5 秒ごとに 5V・VBUSVALID・4P2 の上限・ハブと子機の有無を記録）:

| 試したこと | 5V | ハブ・子機 | 上限 |
|---|---|---|---|
| `nmcli radio wifi off` を 40 秒 | 消えない | 残る | 480 mA のまま |
| logind に蓋を無視させて、蓋を閉じる・開ける | 消えない | 残る | 480 mA のまま |

わかったこと:

- **ハブ（SUNEAST SE-RU3HUBA4A3、中は Huasheng 214b:7250）をつないだままなら、眠っている間も 5V が来ている**（起きた瞬間にある）。4P2 の上限は眠って起きても 480 mA のまま。眠る前後で直すものはない
- brain-watch は眠っている間は記録しないので、`src=batt` が並んでいても「眠っている間に 5V がなかった」とは読めない。過去の `src=batt` はハブの抜き差しのときと見ている
- 見張りピンは、そのときの負荷のもとでの電池の電圧を見ている。5V があると高めに出て、電池だけになるとすぐ下がる（`1111` → `0011` が何度も）。起きる処理で電流が増えた瞬間はさらに下がる。アルカリ電池は休ませると少し戻る

起きたあと Wi-Fi が戻らないことがある（2026-10-15 00:05、ハブはつないだまま）:

- rtl8xxxu66 には suspend・resume の処理がない。起きるときに USB の層がドライバを外し、子機をリセットして probe をやり直す（`usb 1-1.3: disconnecting` → `Device still attached, trying to reset`）
- やり直しの中で、ファームウェアの書き込みが `rtl8xxxu_writeN: Failed to write block at addr: 1d00 size: 0080` で失敗し、`probe of 1-1.3:1.0 failed with error -11`。インターフェースがなくなり、NetworkManager は何もできない
- 毎回ではない（それまでの眠りでは戻っていた）。子機をハブから抜き差しすると戻った
- 手当て（2026-10-15）: `system/usr/lib/systemd/system-sleep/brain-wifi-reprobe` が起きたときに `brain-wifi-reprobe` を別のユニットで起こし、30 秒の間に「rtl8xxxu66 が受け持つはずなのにドライバのない USB の子機」を 3 秒続けて見たら `authorized` を 0→1 にする（2 回まで）。ドライバを手で外して試し、3 秒後に初期化し直して Wi-Fi が戻った。根本は、ドライバがファームウェアの書き込みの失敗をやり直すこと（手をつけていない）
- **本当に失敗したときは `authorized` の付け直しでは戻らなかった**（2026-10-15 11:43）。入/切で眠らせ、キーで起こすと `Failed to write block at addr: 1880` → -11。`brain-wifi-reprobe` は 4 秒後に付け直し、ドライバはつき、NetworkManager も `disconnected` まで来た。しかし 2 分たってもビーコンを 1 つも受けず（`REGDOM-CHANGE init=BEACON_HINT` が出ない）、自動の接続も始まらなかった。子機をハブから抜き差しすると 1 秒でビーコンを受け、10 秒でつながった。失敗した書き込みのあと、子機の中が電源を切るまで戻らないらしい
- ソフトで子機の電源を切り直せる（2026-10-15 に確かめた）: ハブ（214b:7250）は `wHubCharacteristic` 0x00e0 で、全ポートまとめての電源切り（ganged）。`/sys/bus/usb/devices/1-1:1.0/1-1-portN/disable` に 1 を 4 ポートすべて書くと、ポートの状態が 0000（power も落ちる）になり、0 に戻すと子機は新しいデバイスとして見つかり直し、約 14 秒でつながった（`Path A RX IQK failed!` が 1 回出たが、つながった）。ハブにほかの機器をつないでいると、それも一緒に切れる
- 手当てをこれに替えた（2026-10-15）: `brain-wifi-reprobe` は、ドライバのない子機を 3 秒続けて見たら、その子機のハブのポートを全部 `disable` にして 2 秒後に戻す（ハブを通っていなければ前と同じ `authorized` の付け直し。見張りは 60 秒、2 回まで）。ドライバを手で外して試すと、3 秒後に電源を切り、子機は新しいデバイスとして見つかり直し、外してから約 23 秒でつながった。本当に失敗したときに戻るかは、次に起きたときに `journalctl -u brain-wifi-reprobe` で見る
- **本当に失敗したときも戻った**（2026-10-16 08:41、deep の level 2 から キーで起こした）: 起きて 2 秒で `Failed to write block at addr: 1400` → -11。`brain-wifi-reprobe` が 3 秒後に電源を切り、子機は 1 秒で見つかり直してドライバがつき、起きてから約 1 分 40 秒でつながった
- **2 秒では足りないことがあった**（2026-10-17、動いている最中にハブを挿したとき）: 挿した直後、やり直しの 2 回（どれも約 3 秒の電源切り）、手の抜き差し（約 2 秒）と、-11 が 4 回続いた。9 秒抜いていたらつながった。切る時間を 8 秒に、見張りを 90 秒・3 回までにした。延ばしたあとは、挿した直後の -11 から 1 回で戻った（[wifi-rtl8188eu.md](wifi-rtl8188eu.md)）

## CPU クロックを変える手がかり

- クロックの木は分周で下げられる: `cpu_pll` の分周（`HW_CLKCTRL_CPU` の DIV_CPU、6 ビット）を変えれば 454.7 / 227.4 / 151.6 / … MHz。`mxs_clk_div` は `set_rate` を持つ
- HBUS は CPU から分周しているので、CPU を下げると HBUS（DMA・LCD・SD などのバス）も下がる。LCD のちらつき・音の途切れに注意
- 2015 年に上流へ i.MX23/28 の cpufreq-dt 対応（VDDD などの mxs レギュレーター + OPP）が提案されている。OPP は 261.8 / 360 / 392.7 / 454.7 MHz を 1.35 / 1.35 / 1.45 / 1.55 V。レビューで「EMI が 196 MHz を超えるなら VDDD を 1.55 V より下げない」という指摘あり。NXP のフォーラムには 454.7 MHz 以外で固まったという報告もある
- 電圧を下げないと、クロックを下げても省電力の効きは小さい（アイドル時は WFI で止まっているので、もともと CPU はあまり食っていない）

## 進め方（案）

1. 測り方: 電池の見張りピンが落ちるまでの時間で比べる（粗いが実際の持ち時間がわかる。USB 電流計はない）
2. 何が電気を食っているかを先に見る（バックライト、Wi-Fi、CPU の負荷）
3. CPU クロック: 電圧はそのままで分周だけ下げ、安定するか見る → VDDD も下げる
4. サスペンド: 蓋と入/切で眠って起きるところまでできた（上）。`deep` を深くするパッチ（0009）で、DRAM をセルフリフレッシュにして眠り、キーで起きるところまで確かめ、眠り方の既定を `deep` にした（[power-wince.md](power-wince.md) の「deep を作る」）。眠っている間の電池の減りは、テスターがないので見張りピンで粗く比べる
5. 電池残量: 見張りピンの 4 段階を Linux の power_supply として見せる（小さなドライバか、ユーザー空間で）
